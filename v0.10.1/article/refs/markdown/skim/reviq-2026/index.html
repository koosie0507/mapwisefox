Reporting synthesises the extracted data and documents the entire process—most prominently via a Preferred Reporting Items for Systematic Reviews and Meta-Analyses (PRISMA) 2020 [4,5] flow diagram—so that the review can be audited and replicated. Each phase generates artefacts—decision logs, conflict records, agreement statistics, and PRISMA counts among them—which must be internally consistent and accessible for replication.

    Since 2007, SLRs have become a widely adopted research method­ ology in the field of software engineering [6]. Subsequent work has highlighted both their increasing utilization and the recurring method­ ological challenges associated with them [7,8]. A primary concern in this context is the issue of tooling. When we conducted an SLR on a JVM-related topic, we initially documented decisions using a shared spreadsheet. It soon became evident that this approach was inadequate—parallel edits resulted in merge conflicts, the 𝜅 computa­ tion required re-derivation with each decision change, and the PRISMA numbers in the manuscript frequently diverged from the actual counts until discrepancies were identified. This experience, which appears to be common among software engineering researchers [9,10], prompted the development of ReviQ.

    Numerous tools have been developed to address various aspects of this issue. Marshall et al. [11] offer a systematic feature analysis of ex­ isting SLR tools, while Al-Zubidy et al. [12] identify a prioritized set of value-added requirements for SLR tooling infrastructure. Rayyan [13] has emerged as the most widely adopted screening tool, featuring an intuitive web interface with semi-automated duplicate detection and label-based filtering; however, it is cloud-hosted and does not support phases beyond screening. StArt [14] encompasses the entire systematic reviewing process, including quality assessment (QA), and has recently incorporated snowballing support; nonetheless, it does not compute inter-rater agreement nor generate PRISMA 2020 diagrams. Parsifal1 provides a web-based, protocol-driven workflow with quality assessment but lacks snowballing, 𝜅 calculation, and any form of replicationpackage export. Covidence2 is extensively utilized in the health sciences and offers a refined dual-reviewer workflow with PRISMA output, yet it is a commercial cloud product with a free tier limited to a single review. Table 2 presents a comparison of features across these tools.

    We developed ReviQ to address the existing gaps: a single, locallydeployable application that encompasses all phases of the Kitchenham and Charters methodology, calculates 𝜅 with confidence intervals, gen­ erates PRISMA 2020 diagrams from live data, and consolidates the entire project state into a portable replication package. The tool oper­ ates within Docker, stores all data in a local SQLite database, and does not connect to any external servers.

Section 4 dis­ cusses the tool’s research and educational impact, its positioning against related tools, and current limitations. Section 5 concludes.

    2 . Software description¶

    2.1 . Software architecture¶

    ReviQ is a Docker [15] application comprising two containers, as il­ lustrated in Fig. 1. The first container operates Nginx, which serves the React single-page application and reverse-proxies /api/* requests to the second container, a FastAPI [16] service implemented in Python 3.12. All state data is maintained within a SQLite database on a desig­ nated Docker volume ( reviq-db-data ), ensuring data persistence across container rebuilds. Initiating the application merely requires execut­ ing docker compose up --build ; there is no necessity for configuring accounts, application programming interface (API) keys, or external databases.

    The backend comprises ten route modules—one per SLR phase plus cross-cutting concerns like kappa , export , and report —and two service modules ( bibtex_service for parsing and deduplication, kappa_service for agreement statistics). The database schema is struc­ tured with 16 SQLModel [17] tables that align with the SLR process, encompassing projects, reviewers, inclusion/exclusion/QA criteria, pa­ pers, reviewer decisions, final decisions, conflict logs, QA scores, ex­ traction fields and records, snowballing iterations, taxonomy entries, database search strings, and paper–database links. The frontend operates exclusively through the REST API, with React Query managing all data retrieval and cache invalidation, thereby ensuring that the user interface is promptly updated upon the recording of a decision.

    2.2 . Software functionalities¶

    ReviQ realises the SLR methodology as eight sequential phases that map onto the three main phases introduced in Section 1: Phase 1 (project setup) corresponds to Planning ; Phases 2–7 (import, screening, eligi­ bility, snowballing, quality assessment, and data extraction) constitute Conduct ; and Phase 8 (results and PRISMA visualisation) constitutes Reporting . At the top of each phase page, a statistics bar displays real-time counts (retrieved, unique, dupli­ cates, included, excluded, undecided), providing the reviewer with a continuous sense of progress.

    Phase 1—Setup. The researcher initiates a project by establishing a title, description, and the name of the lead researcher, and registers up to five reviewers. Inclusion and exclusion criteria are delineated for each phase (screening or full-text), with each criterion assigned a la­ bel (e.g., E3 ) and a concise, human-readable name that subsequently appears in the exclusion breakdown of the PRISMA diagram. Quality assessment criteria are configured with a maximum score of either 0.5 or 1.0. Taxonomy categories (e.g., “Research Type” with values such as “Evaluation Research”, “Solution Proposal”, etc.) and custom extraction fields (free text, number, boolean, dropdown) are also defined at this stage. Finally, for each database, the researcher documents the search string, filter settings, search date, and result count—this metadata is directly incorporated into the generated protocol report.

    Phase 2—Import. BibTeX files are uploaded for each database from a directory on the host machine. ReviQ processes these files using bibtexparser [18] and performs deduplication across databases in two stages: initially based on the normalized Digital Object Identifier (DOI; converted to lowercase and stripped of whitespace), followed by a com­ posite key of normalized title and normalized venue for entries lacking a DOI. The normalization process removes punctuation and collapses whitespace, thereby addressing minor formatting discrepancies between databases (e.g., “Proc. ICSE” versus “Proceedings of ICSE”). Each iden­ tified duplicate is logged with the citekey of the retained original; reviewers have the option to examine this log and override individual de­ cisions if the heuristic proves incorrect. Language detection via langid flags non-English abstracts, facilitating the efficient application of ex­ clusion criterion E3. A many-to-many link table ( PaperDatabaseLink ) records which databases identified each paper, enabling the calculation of per-database precision and recall in Phase 7.

    Phase 3—Screening. Each reviewer independently categorizes every paper as Include (I), Exclude (E), or Uncertain (U), with the option

    to select the governing criterion (e.g., E2 —insufficient focus) and pro­ vide a free-text rationale. Papers are presented individually, displaying their title, authors, year, venue, abstract, and source database; a fil­ ter bar at the top facilitates narrowing the list to undecided, included, excluded, or uncertain items. Decisions are recorded per reviewer in the ReviewerDecision table. The backend system compares decisions between the two primary reviewers and identifies disagreements as con­ flicts. These conflicts are displayed in a dedicated conflict tab (Fig. 4), where each conflict shows the paper title, both reviewers’ decisions with their rationales side by side, and controls to resolve the conflict through discussion or arbitration. The resolution method and an optional note are documented in the ConflictLog table. Decisions can be exported as a JavaScript Object Notation (JSON) file, allowing co-reviewers work­ ing on separate machines to exchange them via email or shared drives and import them back; the source_file field on each imported decision preserves provenance.

    Fig. 3 presents the screening view of Phase 3, with the paper list, per-paper decision badges, the total/undecided/included/excluded/un­ certain counters, and the filter bar used to narrow the list during the review. Fig. 4 illustrates the conflict resolution view, displaying both reviewers’ decisions for a disputed paper alongside their rationales and the controls used to record the resolution.

    Phase 4—Eligibility. The same decision-making process is applicable to the full-text assessment, utilizing the inclusion and exclusion criteria established in Phase 1. Articles may include a full-text URL for expedited access or be marked as inaccessible if the full text cannot be obtained.

    Phase 5—Snowballing. Forward and backward citation chasing is con­ ducted in accordance with Wohlin [3]. Each iteration is represented as a distinct entity within the database. The researcher imports a new BibTeX batch labeled snowballing:N (where 𝑁 denotes the iteration number), which subsequently undergoes the standard screening and eligibility process. The iteration overview (Fig. 5) illustrates, for each iteration, the number of candidates retrieved, decided, included after screening, excluded, and those still undecided, along with a saturation indicator. When an iteration results in zero new inclusions, the researcher may designate it as saturated, indicating that the snowballing process has reached convergence.

    Phase 6—Quality assessment. In the evaluation process, included pa­ pers are assessed according to the QA criteria established in Phase 1. Each criterion is assigned a score of 0, 0.5, or 1 by individual reviewers. These scores are then normalized to a percentage and categorized as high (≥ 75% by default), medium (≥ 50%), or low , with both thresholds being adjustable for each project. A summary view provides an overview of the score distribution across all papers; Fig. 6 shows this distribution for the validation SLR.

    Phase 7—Data extraction. The extraction schema delineated in Phase 1 accommodates four distinct field types: free text, numerical, boolean, and dropdown with project-specific option lists. Taxonomy categories furnish an additional structured classification layer. A card view enumer­ ates all papers, accompanied by a progress badge indicating the number of fields completed; a table view offers a spreadsheet-style overview of all extraction records, which can be exported as comma-separated val­ ues (CSV). Fig. 7 illustrates the Research Type and Contribution Type taxonomy distributions for the validation SLR.

    Phase 8—Results. The output is organized into three tabs. The PRISMA Flow tab presents a PRISMA 2020 [4] diagram as an inline SVG, featuring two parallel streams (database search and snowballing) and exclusion breakdowns per criterion. This diagram is available for download in both colour and greyscale variants suitable for publication.     4 . Impact¶

    From a research standpoint, ReviQ significantly reduces the barriers to conducting methodologically rigorous systematic literature reviews. The integrated 𝜅 computation eliminates a step that researchers fre­ quently defer to a separate spreadsheet, often resulting in inconsistent calculations—sometimes applied to an incorrect subset of papers, some­ times using a 2×2 matrix when a 3×3 matrix would be more appropriate, and occasionally omitted altogether. The live updates of 𝜅 and PABAK as decisions are recorded facilitate continuous monitoring of agreement throughout the review process, rather than solely at its conclusion.

    The generation of the PRISMA diagram from the same database that stores the decisions ensures that the numbers in the diagram are consis­ tent with the decision log [24]. This provides stronger assurance than a manually drawn figure, as our pre-ReviQ experience demonstrated that altering a single screening decision could inadvertently invalidate the PRISMA counts in the manuscript, with discrepancies only becoming apparent during a meticulous final review—if at all.

    The replication-package export consolidates the entire project state into a versioned ZIP archive, thereby supporting the reproducibility requirements that several software engineering venues have begun to mandate. When published alongside an SLR, this package enables other

    researchers to verify reported counts against actual decisions, reuse the extraction data for meta-analyses, or extend the review with additional snowballing iterations.

    The decision to run all processes locally was intentional. Researchers at institutions with restrictive data policies—or those handling embar­ goed submissions—may be prohibited from uploading paper metadata to a third-party cloud service. ReviQ does not contact any external server. The Docker-based deployment ensures consistent behavior across Linux, macOS, and Windows without necessitating the manual installation of Python, Node.js, or any other runtime.

    Beyond its primary research application, ReviQ can also serve as an educational tool. By enforcing the Kitchenham and Charters phase struc­ ture and making each step explicit—criteria definition before screen­ ing, dual-reviewer decisions before conflict resolution, and QA scoring before extraction—it provides students with a concrete, interactive walkthrough of the SLR methodology.

    Discussion and comparison with related tools¶

    No single feature sets ReviQ apart from existing tools; the differ­ entiator is their combination. Among the surveyed tools (Section 1, Table 2), Rayyan [13] offers a polished cloud screening experience with label-based filtering but is confined to the screening phase, does not compute inter-rater agreement, and does not produce PRISMA dia­ grams. Covidence offers a refined dual-reviewer workflow with PRISMA output, but is a commercial cloud product and—in the free tier—is limited to a single review per researcher. Among free, open-source tools, StArt [14] covers the broadest set of phases and has recently added snowballing, but does not compute 𝜅 or PABAK, does not produce PRISMA 2020 diagrams, and offers no equivalent to a singlefile replication-package export.     workflow with quality assessment but lacks snowballing, agreement statistics, and replication-package export. ReviQ therefore combines local-only deployment, end-to-end phase coverage, integrated 𝜅 and PABAK with confidence intervals, PRISMA 2020 generation from live data, and a single-file replication-package export—each available else­ where in isolation but, to our knowledge, not jointly in a free and open-source tool.

    The validation SLR was a small but realistic exercise of these capabil­ ities. Screening agreement settled at the lower end of the Landis–Koch “moderate” band ( 𝜅 = 0 . 509); had this been computed only at the review’s end, it would have been too late to inform reviewer calibra­ tion. Because ReviQ surfaced 𝜅 as decisions were recorded, the value prompted a mid-review conversation about how strictly to apply crite­ rion E2 (insufficient focus); we found this more informative than a single end-of-review snapshot. The 19 screening conflicts were all resolved by discussion rather than third-party arbitration, suggesting that screening disagreements are typically matters of interpretation rather than sys­ tematic error. Of the four snowballing iterations, only iterations 1–3 contributed new included papers; iteration 4 yielded zero inclusions and was marked as saturated, which made the decision to stop a quantitative rather than an intuitive one. The PRISMA diagram, regenerated from live data at submission time, agreed with the manually verified counts—a check our pre-ReviQ experience suggests would otherwise have required a separate manual reconciliation pass.

    Limitations. Several limitations remain. The asynchronous collabora­ tion model, which relies on JSON export/import, works well for teams of two or three but does not scale for larger groups; a Git-based or sharedfilesystem sync layer is a planned enhancement. Currently, only BibTeX is supported as an import format; incorporating RIS and CSV import capabilities would enhance compatibility with databases that default to alternative formats. ReviQ does not yet provide AI-assisted screen­ ing, although the decision data stored within ReviQ, including paper metadata, reviewer labels, and rationales, could serve as training data for active-learning rankers. The PRISMA diagram presently implements only the two-stream layout as prescribed by the PRISMA 2020 statement (databases + other methods); reviews with more complex identification paths would require manual adjustments to the generated SVG. Lastly, ReviQ does not currently enforce blinding between reviewers—both re­ viewers can view each other’s names, although they cannot access each other’s decisions until they are exchanged.

    5 . Conclusions¶

    We have introduced ReviQ, an open-source SLR workbench that com­ prehensively addresses all eight phases of the Kitchenham and Charters methodology within a locally-deployed web application. The primary contributions of ReviQ, which extend beyond the capabilities of existing tools, include: (i) integrated computation of Cohen’s 𝜅 and PABAK with confidence intervals, updated in real-time as decisions are made; (ii) automatic generation of PRISMA 2020 diagrams with exclusion counts per criterion, rendered as publication-ready SVGs; and (iii) a versioned replication-package export that consolidates all project data for archival purposes or transfer.

    We validated the tool through application to a real SLR in the soft­ ware engineering domain. This review involved two reviewers, five databases, 519 retrieved records, four snowballing iterations, and 40 in­ cluded studies. The moderate screening agreement ( 𝜅 = 0 . 509) and the resolution of 19 conflicts via the built-in user interface demonstrate the tool’s capability to manage typical levels of disagreement encountered in practice. The PRISMA diagram and a 22-page protocol report were

    generated directly from the stored data, affirming that ReviQ can facili­ tate a review from initial setup to publication-ready outputs without the need for external tools.

    Future developments will focus on enabling real-time collaboration between reviewer instances, supporting RIS/CSV import, incorporating AI-assisted pre-screening, and implementing reviewer blinding.
